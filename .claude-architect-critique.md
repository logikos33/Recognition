### B. Registry = `public.trained_models` keeping `{schema}.models` untouched -- APPROVE with 1 adjustment

This is the pragmatic correct decision. The two tables serve distinct purposes:

### C. Progress callback via HMAC -- APPROVE with 3 adjustments

The HTTP callback + HMAC job-scoped token is correct for the MVP. Poll SSH adds network complexity; progress via R2 adds latency and cost for frequent updates. The watchdog poll as backup is sound.

**Defect C-1: No expiry on the HMAC token.** `HMAC(JWT_SECRET_KEY, job_id)` is deterministic and never expires. If a GPU instance is compromised, the token remains valid indefinitely.

**Defect C-2: No input validation on the callback payload.** The endpoint must reject `progress > 100`, malformed `metrics`, and oversized `error_message` to prevent DB pollution from a compromised or buggy GPU script.

**Defect C-3: No rate-limiting on the callback endpoint.** Without JWT, the endpoint is a public POST. Without rate-limiting, it is a trivial target for abuse.

**Correction:** (1) Include a timestamp in the HMAC payload: `HMAC(key, f"{job_id}:{issued_at}")`, reject if `now - issued_at > 24h`. Alternatively, generate a random token per job, store in `training_jobs.callback_token` (simpler, revocable on stop). (2) Validate: `0 <= progress <= 100`, `len(error_message) <= 500`, `metrics` is dict with known keys. (3) Add `limiter.limit("60/minute")` to the callback endpoint.

### D. Migration 094: ALTER COLUMN video_id DROP NOT NULL -- APPROVE with 1 adjustment

`DROP NOT NULL` on an already-nullable column is a PostgreSQL no-op (succeeds silently), so re-running is safe. The `DO $$` pattern used elsewhere in this codebase (e.g., `011_active_learning.sql:6-9`) catches `duplicate_column` / `duplicate_object` exceptions correctly. Wrapping the DROP NOT NULL in `DO $$ ... EXCEPTION WHEN others THEN NULL; END $$` is idempotent.

The runner at `railway_start.py:74-84` executes the entire file as one `cur.execute(open(f).read())` + `conn.commit()`. On failure, it does `conn.rollback()` and checks for `'already exists'` or `'duplicate'` in the error message. `DO $$` blocks that catch their own exceptions never propagate to the outer transaction, so the runner's rollback path is not triggered. This is safe.

**Defect D-1: The runner's error handling at line 80-84 has a gap.** If a statement fails with an error that does NOT contain `'already exists'` or `'duplicate'` (e.g., a CHECK constraint violation, a missing referenced table), the runner logs `"  ❌ {e}"` but **continues to the next file**. It does NOT abort. This means a failed migration 094 would be skipped, and migration 095 (which depends on 094's columns) would also fail. The runner would log errors for both and keep going, leaving the database in an inconsistent state. This is a pre-existing design flaw, not introduced by the plan, but the plan should acknowledge it as a risk and document the manual verification step after deployment.

**Correction:** Add a note in the runbook: after deploying migrations 093-101, verify all 9 applied successfully by checking column existence (e.g., `SELECT column_name FROM information_schema.columns WHERE table_name='training_frames' AND column_name='source'`). Consider adding an abort-on-error flag to the runner in a follow-up PR.

### F. Auto-capture in both inference paths -- ADJUST (duplication bug)

**Defect F-1 (CRITICAL): Double-capture from the same detection event.** Tracing the flow:

1. `inference.py:213-214` -- Celery `inference_loop` detects violation, calls `_save_alert()`, publishes to Redis channel `det:{camera_id}`.
2. `socket_bridge.py:173-181` -- Bridge receives `det:{camera_id}`, calls `_maybe_verify_detections()` -> `_create_alert_and_verify()`.

Both paths fire for the **same** detection within milliseconds. If auto-capture is hooked into BOTH `_save_alert()` AND `_create_alert_and_verify()`, every violation produces two `training_frames` rows. The plan's rate-limit (1/min/camera via Redis) has a TOCTOU race condition: both hooks check the rate-limit key before either sets it (they run in different threads/processes within ~10ms of each other).

Moreover, `_create_alert_and_verify()` does not have access to the raw frame (numpy array) -- it only receives detection metadata from Redis. Auto-capture from this path would require re-downloading the evidence image from R2, which is wasteful and error-prone (the upload from `_save_alert` might not have completed yet).

**Correction:** Hook auto-capture in `_save_alert()` ONLY (Celery path). It has direct access to the frame. Remove the auto-capture hook from `_create_alert_and_verify()`. The plan's `POST /api/v1/alerts/<id>/add-to-training` endpoint provides the explicit manual path for bridge-created alerts. Use `SETNX` (atomic set-if-not-exists) for the rate-limit key instead of GET+SET to eliminate the race condition.

**Volume concern:** 12 cameras * 24h * (1 capture/min) = 17,280 frames/day. Add `MAX_AUTO_CAPTURE_PER_DAY_PER_CAMERA` env var (default 200) as a hard cap.

The plan adds `width INTEGER, height INTEGER` to `training_frames` (migration 094) and backfills `r2_key = filename WHERE r2_key IS NULL`. The COCO export converts normalized YOLO coordinates to absolute pixels using width/height, with a fallback that reads from R2.

(4) In `build_dataset_version_v2`, batch the R2 dimension fallback reads with concurrency (e.g., `ThreadPoolExecutor(max_workers=10)`) to avoid sequential HTTP latency.
